# Security review, November 2026

Scope: every hub route, host script and updater path added or changed between `v0.1.0-beta.17` and the review commit
(guided migration runs, host-report and verify ingest, the `coolify-host-loop` script, importer and volume-stream routes,
server reboot / patch / cleanup / compose restart heal, the updater and its host-files path, the migrator installer).
Method: read the code, walk every route's guard chain, exercise the shell builders and scripts with hostile input.

## What was checked

| Area | Result |
| --- | --- |
| Authentication of token routes (`/import/migration/*`, `host-report`, `verify`, `vx/*`) | Every route sits behind `MigrationTokenGuard`; the op comes only from the token (`@MigrationOp`), never from a param, query or body. A malformed token is rejected before any database read. All failures share one 401. |
| Authorization and IDOR | Run routes load the run by id, then require creator ownership plus team membership plus `apps:config` and `databases`; a foreign run is a 404. `serverMap` targets, attached host inventories and object migrations are checked against the run's team or run id. Token routes re-authorize the actor against the target server's team on every call. Reboot, patch and cleanup require `servers:ops` and the `deploy` scope for mutations. |
| Scopes | `deploy`, `read:secrets` and `admin` are enforced per route and again inside the run facade (so an MCP call with a weaker advertised scope still fails closed). The point-of-no-return and decommission approvals are refused over MCP. |
| Rate limits and size limits | Token and signed-URL routes are throttled per IP; host-report body is capped at 1 MiB and `text/plain` only; the probe sink and certificate staging are byte-capped while streaming; artifact staging has a byte cap and a disk headroom check; JSON bodies are strict zod schemas with bounded arrays. |
| Replay and idempotency | Host report lines are upserts keyed by run, step, host and kind; reboot requests are guarded by a unique active-row constraint and audited before they run; approvals are hash-bound and single-use (`updateStepIf`); relay and artifact URLs are HMAC-bound, short-lived and (relay) single-use per role. |
| Shell injection in generated scripts | Host loop, freeze, launcher, inventory, vx apply, stack converge, compose restart heal, cleanup, reboot and decommission builders validate every interpolated value against a narrow charset and embed it single-quoted; per-host values read from the Coolify database are validated in the shell before they reach `ssh`. One gap found in the patch builders (below). |
| Secrets | The migration token is never on an argv (stdin, environment or a curl config on stdin), is stored only as a SHA-256 hash, is shown once, and is absent from events, audit entries and logs. Staged ACME private keys are encrypted at rest and blanked once applied. |
| SSRF | Source API clients pin the connection to a guarded DNS lookup, refuse redirects and cap the response; the cutover probes connect only to a public, hub-stored server address (never a request input). |
| Path traversal | Staging paths are built only from hub-side ids; volume names, itemRefs and host-file manifest paths are validated (manifest paths are whitelisted, sorted, unique, signed and hash-checked). |
| Client IP trust | The forwarding-chain logic is fail closed: the rightmost entry only, trusted peers only, Cloudflare mode only when the observed hop is a published edge range; the web server rewrites the chain before the hub sees it. |
| OAuth | The login state is bound to the starting browser with a single-use httpOnly nonce cookie whose hash is inside the signed state. |

## Found and fixed

1. **Updater accepted any queued target version** (`scripts/update.sh`). The target of a queue job was written to `.env`
   as `TUGRA_VERSION`, used as an image tag and stored in the status key without validation; a value with spaces, `$(...)`
   or other shell or dotenv syntax went straight through when the job carried no signed host-files digest. The updater now
   refuses any target that is not a plain version string (`^[0-9A-Za-z][0-9A-Za-z.+-]*$`, 64 characters at most) before it
   snapshots, writes or pulls anything. Test: `update-script.spec.ts`, "refuses a targetVersion that is not a plain version string".
2. **Package names ending in a dash** (`server-ops/patch-script.ts`). `apt-get install --only-upgrade <pkg>-` reads the
   trailing dash as "remove this package", so the single-package and phased upgrade routes, available to any member with
   `servers:ops`, could be turned into a package removal. A name can no longer end in `-`. Test: `patch-script.spec.ts`.

## Reviewed and accepted

- The hub base shown in a migration command comes from `HUB_PUBLIC_URL`, falling back to the request host when it is unset.
  The value is charset-checked before it is embedded, and the only request that can influence it is the authenticated
  owner's own, so there is no cross-user vector. Setting `HUB_PUBLIC_URL` (the installer does) removes the fallback.
- `StrictHostKeyChecking=accept-new` in the host loop trusts a source host on first contact. The loop keeps its own
  `known_hosts` file, so a changed key is refused afterwards.
- A staged source certificate is accepted when it covers any hostname of the operation, including a wildcard: the source
  host is the legitimate holder of that key, and nothing is served until the operator seeds it.

No customer data, hostnames or addresses are used in this review.
